# Tech Research UI Optimization Plan

Revised 2026-11-07 against the current repository. Improve research readability and feedback in the existing battle console, preserving gameplay, selection, pause, refunds and keyboard navigation. Implemented on 2026-11-07, including the subsequently requested ImageGen icon set. Validation evidence and pre-existing suite failures are recorded below.

## 1. Verified baseline and corrections

| Finding | Evidence and implication |
| --- | --- |
| Active project information is hidden | `ResearchPanel._ready()` calls `_status.hide()`. `refresh()` updates the text and parent visibility, but never shows the label. The existing Bastion active-research capture also shows the sparse icon/bar/cancel footer. |
| The standalone Tech view can display selection health | `_build_info()` sets `_health_dirty`; `_build_research()` hides health, then `_refresh_health()` restores visibility from the retained selection. Shields share this refresh path and need the same protection. Reproduce both before fixing. |
| Current research is faction-specific | `TechnologyCatalog.FACTION_TECHNOLOGIES` exposes six branches for Bastion, six for Helix and five for Frontier, plus Coordination. Weapons/Armor I–III remain historical data; current tile tests explicitly reject those branches. Remove multi-tier pips from this scope. |
| Coordination enables queued dependencies | `planned_technologies()` includes active and queued projects. Dependent research becomes queueable as soon as Coordination is purchased; it does not require Coordination to finish first. |
| Doctrine exclusion has two meanings | A queued or active rival reserves the choice; cancelling it restores eligibility. A completed rival permanently excludes the other doctrine. The current generic “Permanently excluded” reason obscures this distinction. |
| Queue preview is stale | `ResearchQueuePreview.gd` accesses retired `weapons`, `armor`, `service`, `doctrine` and `dual_purpose_aa` branches, expecting seven queued projects. Repair its fixture before treating it as acceptance evidence. |
| Keyboard claims need correction | Queue digits are drawn with `show_hotkey()` but the reviewed research path has no numeric cancellation handler. Do not advertise them as shortcuts. `T` is used by building/ability commands; do not introduce a global Tech binding. |
| Rendering coverage is incomplete | `HudConsolePreview.gd` currently captures Bastion/Frontier at 720p/150% and Helix at 1080p/100%, in English and Chinese. It does not establish all-faction coverage at every resolution or any 4K coverage. |

## 2. Constraints and chosen design

- Keep research choices and cancellation controls inside the bottom HUD. Preserve directly accessible labelled tabs; add no floating menus, scrolling, nested navigation or Back submenus. The top widget remains a status indicator and launcher.
- Preserve the `HudLayout.CONSOLE_HEIGHT` budget of 246 logical units and the existing `<= 246.5` geometry tolerance. Verify the actual window size and UI scale in each rendered case; do not equate logical units with physical screenshot pixels.
- Keep every main research choice's picture, name and both resource prices visible in every state. Retain the existing one-line title/ellipsis convention, with the full title in its tooltip and accessible description. Do not strike through titles or cover prices with badges.
- Keep one responsive choice grid. Use compact “Core” and “Doctrine” labels within the existing tile footprint, with doctrine choices adjacent in catalog order. Use “Choose one” on both doctrine choices instead of an extra OR-divider cell that consumes grid space or breaks reflow.
- Use a static progress strip and a restrained background fill for active research. Use no colored state borders, continuous pulsing or camera movement. Preserve clearly visible keyboard focus indicators and existing `HudMotion` completion feedback/settings.
- Use `BattleTheme` fonts, sockets, fills and faction accents. HUD housing textures remain generated by `tools/ui/generate_hud_kit.py`. Per the user's subsequent ImageGen request, research portraits now use a dedicated set of 18 transparent raster emblems; these are separate from the HUD kit.
- Preserve the existing research purchase/cancel APIs, FIFO order, prepaid amounts, cascading refunds and save schema. Do not add a queue cap or gameplay tiers to fit the layout.

### Tile states

Resolve purchased states first, then exclusion and other blockers. Determine state from research IDs and catalog requirements; do not parse translated reason text. Keep `queue_reason()` authoritative for purchase eligibility.

| State | Visible treatment | Behavior and accessible detail |
| --- | --- | --- |
| Available | Normal tile with icon, title and price | Click/Enter starts or queues through the existing API. |
| Active | `32 s` badge and progress strip; paused/stalled symbol when applicable | Disabled purchase; cancellation remains in the footer. Tooltip explains progress, rate and any stall. |
| Queued | `Q1`, `Q2`, etc., matching FIFO position | Disabled purchase; matching footer control cancels and refunds. Queue positions are not key bindings. |
| Completed | High-contrast checkmark and subdued fill | Keep the authored price visible; expose “Completed” in accessible text. |
| Prerequisite missing | Compact lock/requirement cue | Explain the actual missing prerequisite. Buying Coordination immediately makes eligible dependents queueable. |
| Rival reserved | Distinct reservation/lock cue | Identify the active or queued rival and explain that cancelling it releases the choice. |
| Rival completed | Distinct excluded cue | Explain the permanent doctrine exclusion and name the completed rival. |
| Other unavailable | Neutral disabled treatment | Explain missing lab, progression gate or resource shortfall without implying doctrine exclusion. |

At narrow sizes, prioritize state badges over the optional category label. Keep both doctrine choices recognizable and preserve their full exclusivity explanation in tooltips and accessible text.

### Active footer and queue

Keep one horizontal footer: active icon, a flexible text/progress block, active cancel control, then ordered queue controls. Inside the text block, place the project title above a compact ETA/progress/status line, with a slim progress strip. Target a 44–48 logical-unit footer; confirm the total budget with tabs, margins and the widest legal queue before polishing.

- Show the full active title when space allows; ellipsize only that title at constrained widths. ETA, progress and the reason for a stall must remain readable.
- Use `ceil(remaining / research_factor)` for the estimate at current power and `clamp(1 - remaining / duration, 0, 1)` for completion. Handle Coordination's separate timer explicitly. Compute the factor once per refresh and reuse it.
- Label global pause as “Paused”; label a missing completed lab as “Rebuild lab”. Do not claim construction is already underway. A stalled timer is remaining work, not a live wall-clock finish promise.
- Derive “Low power” and its percentage from actual state/rate, not a hard-coded 75%. Handle boosted rates above 100% correctly. When pause and lab loss coexist, expose both conditions in the detailed description.
- Give each supplemental queue shortcut a matching `Qn` badge, icon and accessible cancellation/refund text. Its main choice tile continues to show the technology name and cost. Keep footer controls large enough for mouse and keyboard use; decorative connectors are optional and removed first if space is tight.
- The current largest legal queues, with Coordination active and one doctrine reserved, contain five entries for Bastion/Helix and four for Frontier. Derive fixture contents and payments from the catalog; these are current content limits, not a new queue rule.
- Keep controls alive during the existing 0.25-second refresh. Update labels/fills in place; preserve logical focus when entries shift and choose a valid visible fallback when a focused entry disappears.

## 3. Implementation stages

### Stage 1 — Establish a trustworthy baseline

**Files:** `tests/rendered/ResearchQueuePreview.gd`, `tests/headless/ResearchTilesRegression.gd`, existing research regression suites.

1. Run the current relevant headless suites with the repository-pinned Godot 4.7.2 binary; record baseline failures separately from new failures.

3. Preserve real Tab/Enter/Esc input in the preview. Exercise Coordination cancellation/refunds, independent queued cancellation, active cancellation with FIFO advancement, reservation release, and pause/selection preservation.
4. Add a focused regression for opening standalone Tech with selected units, waiting for the deferred health refresh, and receiving subsequent health/shield changes. Assert the correct bars remain visible when returning to selection.

**Exit:** the fixture reaches its intended scenarios without invalid branch access; the original health/shield failure is reproduced and recorded.

### Stage 2 — Fix standalone Tech identity and health

**File:** `source/match/hud/UnitMenus.gd`.

1. Make `_refresh_health()` respect the standalone research view before deriving visibility from `_selection`; suppress both health and shields in that view.
2. Preserve the selected units and normal selection subscriptions. Do not solve the artifact by clearing the player's selection or disabling health updates globally.
3. Keep the left bay concise: Technology title, existing tech artwork, and faction identity if space permits. Add no verbose overview or extra navigation hierarchy.
4. Verify opening and closing through existing controls while running and paused, including repeated refreshes and switching back to a selected Command Lab.

**Exit:** no unit health/shield bar appears under Technology; selection health/shields resume correctly on return; pause state is unchanged.

### Stage 3 — Restore active feedback within the layout budget

**File:** `source/match/hud/ResearchPanel.gd`.

1. Replace the hidden-status footer with the bounded layout above. Merely showing the current autowrapped label is insufficient because it can increase minimum height.
2. Add typed/stable node references for the active icon, title, status and progress. Keep display calculations separate from purchase/cancel actions.
3. Render Coordination and ordinary technology consistently across running, paused, low-power, lab-loss and resumed states. Localize templates before formatting values.
4. Reuse queue controls and refresh their numbering, tooltip and accessible text when order changes. Preserve deferred deletion during button signal delivery.
5. Verify the fullest legal queue at 720p/150% before adding decorative styling. Every visible child and focus indicator must fit inside its actual parent bounds; clipping is not a substitute for fitting.

**Exit:** active title, meaningful status, progress, ETA and cancel action are visible; the entire queue fits with stable focus and no console-height increase.

### Stage 4 — Clarify tile states and doctrine choice

**Files:** `source/match/hud/ResearchButton.gd`, `source/match/hud/ResearchPanel.gd`.

1. Implement the state table using a small, explicit presentation-state mapping. Reuse `TechnologyCatalog.exclusion()`, `requirements()` and research state instead of duplicating gameplay rules.
2. Place markers within reserved space so they cannot overlap the title or either price. Keep state information readable on disabled buttons and understandable without color alone.
3. Add Core/Doctrine cues without new grid children, extra tile rows or separate section headers. Retain `_grid` as the tile container and preserve `_fit_grid()` reflow.
4. Explain reserved versus completed doctrine exclusion in the UI while retaining the existing gameplay decision. Update corresponding behavioral assertions if tooltip wording changes.
5. Keep shared `RosterButton` behavior unchanged unless a concrete shared defect requires a separate, tested correction.

**Exit:** all factions expose exactly their authored choices; states are distinguishable; cancelling a reserved doctrine immediately restores its rival; icons, names and prices remain visible.

### Stage 5 — Align top status and localization

**Files:** `source/match/hud/ResearchStatus.gd`, `art/localization/*.tsv`; a small shared presentation helper only if needed by both research widgets.

1. Add the active project's icon to the existing launcher button and style progress using `BattleTheme.bar_fill(BattleTheme.accent())`.
2. Reuse the same icon mapping and time/state formatting as the bottom view. Avoid instantiating a research panel merely to obtain an icon. Extract only the shared presentation code that both views need.
3. Clear stale icons when returning to the available-choices state. Preserve visibility suppression during overlays, notices, assignments and finished matches.
4. Retain the current completion event and `HudMotion` behavior; do not add duplicate completion effects or new looping animation.
5. Add English/`zh_CN` strings to the localization TSV sources, then run `python3 art/localization/build_catalog.py`. Cover composed titles, state text, exclusivity, queue order and accessible descriptions. Do not edit generated `assets/translations/ui.csv` directly.

**Exit:** top and bottom widgets agree on project, rate and state; Chinese text and CJK glyphs render correctly; there are no misleading keyboard shortcut badges.
