# Heavy 2v2 performance and nighttime readability

User goal: sustain **60 fps** at native 3840×2160 on the Ryzen 7 5800X3D / RTX 4090
PC during heavy building and large-army 2v2 matches. Improve nighttime visibility
as part of the same work, then commit and push the verified changes to main.

The user revised the target from 120 to 60 fps after pass 26. The active frame
budget is now **16.67 ms**. Earlier work-log entries and archived reports retain
their original 120 fps thresholds as historical evidence. Workload, resolution,
nighttime readability and delivery requirements remain the same.

The recent setup used Copper Badlands. No recent battle save was found, so a
repeatable heavy fixture must complement the real match setup. Existing four-player
timings use 200 mobile units / 80 structures at 1080p with commander AI disabled;
they cannot establish the requested target.

## Measurement contract

- Native 3840×2160 rendering at 1.0 3D scale, with the current graphics features.
- Four players on two teams, up to the existing 100 mobile / 40 structure limits
  per player. Retain live navigation, collision, weapons, effects, HUD and AI.
- Compare the same seeded workload, camera, graphics and simulation rate before
  and after each optimization. Increased fixture HP may keep load stable, but
  must be recorded and must not suppress combat effects or targeting.
- Measure real rendered production builds serially, with VSync disabled and a
  foreground window. Report cold setup separately from warmed movement, combat,
  dense bases, and nighttime. Reject missing rendered frames or focus losses.
- Record mean/p95/p99 frame times, CPU/GPU timings, workload counts, firing and
  movement activity, and raw samples. Target at least 60 mean fps and p95 frame
  time at or below 1000/60 ms after warmup; report remaining tails honestly.
- Keep gameplay rules and saved-state contracts intact. Do not claim success
  from headless tests, lower rendering resolution, disabled AI, or reduced counts.

## Research used

- [Godot MultiMesh](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html):
  retain shared geometry and spatial batches; make their bounds useful for culling.
- [Godot navigation optimization](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_optimizing_performance.html):
  avoid duplicate path queries and repeated target resets, amortize expensive work.
- [Godot thread safety](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html):
  keep live SceneTree work on the owning thread; parallel jobs must own their data.
- [GDScript static typing](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/static_typing.html):
  use known operand and argument types in hot paths so the VM can select optimized
  opcodes, while retaining generic paths for non-unit combat objects.
- [Crowd Pathfinding and Steering Using Flow Field Tiles, Elijah Emerson](https://www.gameaipro.com/GameAIPro/GameAIPro_Chapter23_Crowd_Pathfinding_and_Steering_Using_Flow_Field_Tiles.pdf):
  shared tile fields and hierarchical routes amortize navigation for large armies.
  A flow-field replacement is a possible architectural follow-up, not an existing
  implementation or a verified speedup in this game.
- [Animated Crowd Rendering, Bryan Dudash / NVIDIA](https://developer.nvidia.com/gpugems/gpugems3/part-i-geometry/chapter-2-animated-crowd-rendering):
  texture-backed animation palettes and compact instance state can move crowd
  posing off the CPU. Current GPU interpolation still computes gait/body poses
  on the CPU; a native bulk solver or GPU pose evaluation is a possible next
  architectural step, requiring visual/socket parity and new complete-frame
  measurements before adoption.
